# Заполнение остатка пачки резервом — 24 октября 2026

Запрос: после исчерпания свежих записей заполнять оставшиеся места той же
пачки старыми, только со свежими счётчиками и всеми прежними ограничениями.

Решение: один дополнительный refresh через существующий VKReadClient,
с принудительным охватом резервного слоя и новым точным fresh_after.
Предыдущий pool очищается до чтения. Полные свежие наблюдения обоих слоёв
допускаются к выбору; сегодняшние сохраняют приоритет, включая обнаруженные
во время этого чтения. Ошибка/budget/stop не разрешают прежний pool.

Обновлять оба слоя заранее в каждой пачке дороже; использовать старые
наблюдения без нового refresh противоречит запросу. Выбран переход по спросу.

План выполнения:
1. Регрессия: три свежих действия и одно резервное; fresh_after, NULL,
   изменившийся порядок счётчиков, stop/429/budget/window/day, квоты и четыре
   попытки, bounded refresh и исходный day plan.
2. Изменить только orchestration Worker и режим refresh резервного слоя.
   Не менять action callbacks, sleep20, retry, 540сек или дневные лимиты.
3. Полный unittest в source-only копиях локально и на VM, независимое ревью.
4. Backup, штатное обновление worker между пачками, проверка сохранности
   истории/плана/квот и рабочего режима. Публикация GitHub отдельно.

Review focus: устаревший pool после частичного API-ответа; свежие посты,
найденные при reserve refresh; переход дня/окна во время чтения; повторное
обновление без прогресса; попытки retry расходуют те же четыре места.
