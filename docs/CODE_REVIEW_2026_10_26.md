исправлены по последующему запросу пользователя и установлены на VM;

Найдены семь воспроизведённых дефектов: два P1 и пять P2. Условие «полная остановка только при критической ситуации» пока не выполняется: добавление отключённого аккаунта и допустимый технический сбой до отправки могут поставить весь worker на бессрочную паузу. Одновременно API CAPTCHA и требование проверки не всегда останавливают дальнейшие запросы. В аналитике обнаружено необоснованное превращение старого незавершённого замера в окончательный отчёт.

Это ревью текущих локальных исходников. Исполняемый код, настройки и история не изменялись; VM не опрашивалась, worker не останавливался и не возобновлялся, реальные действия VK не выполнялись. Локальная папка без `.git`, поэтому соответствие текущему GitHub и установленной VM этим ревью не установлено. GitNexus проверен: `vk_bot` в списке центральных индексов отсутствует.

## Подтверждённые дефекты

### R1 P1 API CAPTCHA и проверка не создают защитную блокировку

Код: `vk_api_read.py:497–509`, `vk_catalog_scan.py:125–138`.

Коды VK 14 и 17 попадают в обычный `VkApiFailure`. Долговременная `safety_lock` записывается только для `VkApiLimited`. Фоновый каталог считает такой результат ошибкой одной группы и запрашивает следующую. Ручной сбор статистики и `LiveReader` аналитики также оставляют общий каталог без блокировки, хотя завершили свой вызов ошибкой. Это позволяет следующему worker продолжить работу после обнаруженной защиты.

В [официальной схеме VK API 5.199](https://github.com/VKCOM/vk-api-schema/blob/333481bd082ad747d4873ef4a77f9247097eeef0/errors.json) код 14 означает CAPTCHA, код 17 — необходимость проверки. Context7 для этой проверки был недоступен из-за квоты; использована первичная схема VKCOM нужной версии.

Воспроизведение: для 14/17 `locks=0`, проверка `require_platform_unlocked()` проходит, вызываются группы 101 и 102. Контрольный код 6 даёт `locks=1` и только первый вызов. Отдельно проверены ручная статистика и автономный `LiveReader` с кодом 14. Все ответы синтетические.

Исправление: типизированная защитная ошибка и сохранение общей блокировки в API-слое; каталог должен прекращать цикл, остальные читатели — сохранять тот же запрет. Не добавлять обход проверки или автоматическое снятие защиты.

### R2 P1 Старый замер становится полным без нового сбора

Код: `vk_analytics.py:79`, последствия в расчётах полноты и регулярности на строках 86–110.

`period_elapsed` сравнивает конец отчётного периода с текущим временем генерации. Но архив известен только на момент чтения. Поэтому незавершённый период становится полным после смены даты, даже если новых наблюдений не появилось. Последующий `report --freeze` может сохранить ложные окончательные ER, П3.3 и П3.2.

Воспроизведение одного неизменного run за `[19 октября, 26 октября)`, завершённого 25 октября в 20:01 YEKT:

| Момент генерации | Полнота | ER | П3.3 | П3.2 |
| --- | --- | --- | --- | --- |
| 25 октября 20:01 | partial | NULL | NULL | NULL |
| 26 октября 08:00 | complete | 1 | 27.7778 | 100 |

База и три сохранённых поста между расчётами не менялись. Публикации после окончания чтения не собирались. Штатные замеры 08/20 имеют конец периода на следующий день, поэтому этот сценарий соответствует используемому формату накопления. Веб-reader уже связывает закрытие периода с `finished_at`, а CLI-калькулятор — нет.

Исправление: подтверждать покрытие периода временем сохранённого сбора, учитывать время наблюдений и завершения обхода каждой группы. Поздняя генерация не должна повышать полноту. Одинаковые snapshots должны давать одинаковые показатели независимо от часов компьютера.

### R3 P2 Добавление отключённого аккаунта может остановить весь daemon

Код: `vk_control.py:304–305`, `vk_accounts.py:139`, `vk_scheduler_state.py:55,182–183`, `vk_scheduler.py:550–552`.

Команда панели сначала публикует аккаунт в реестре, затем создаёт его SQLite. Между этими действиями `refresh_policy()` добавляет новый путь в `state.paths`, а `usage()` открывает базы всех аккаунтов, включая отключённые. Worker получает `SQLITE_CANTOPEN`. Обработчик сохраняет глобальную паузу `OperationalError`, после чего повторно падает при построении статуса по отсутствующей базе; исключение выходит из цикла daemon.

Воспроизведение через настоящие `control.dispatch()` и `worker.tick()` с барьером на границе публикации: новый аккаунт disabled, квоты 0, jobs 0, базы ещё нет — возникает ошибка SQLite 14. После успешного создания базы следующий tick всё равно возвращает `attention`, `paused=OperationalError`.

Исправление: публиковать готовый actor только после создания и инициализации его базы либо ввести согласованное состояние подготовки, которое не включается в бухгалтерию до готовности. Сохранённый план и истории прежних аккаунтов не менять.

### R4 P2 Подклассы OSError ломают разрешённый повтор

Код: `vk_action_retry.py:18–22,131,347–357`, `vk_scheduler.py:50,550–552`.

`retryable()` допускает подклассы `OSError` как технические ошибки, но `safe_failure_reason()` возвращает конкретное имя класса. В `SAFE_REASONS` есть `OSError`, но нет, например, `BlockingIOError`. Поэтому уже допущенный к восстановлению сбой отвергается в `fail_pass()`, выбрасывая новый `RuntimeError` за пределы обработчика действия. Daemon ставит общую бессрочную паузу после первого сбоя.

Воспроизведение через `worker.run_batch()`: один синтетический `BlockingIOError` до intent, один вызов исполнения, actor attempts 0, intent 0, счётчик логических неуспехов 0. Получено `Failure not eligible for bounded recovery`; recovery остаётся running. Применение действующего внешнего обработчика даёт `paused=RuntimeError`. Это доказательство ошибки классификации; частота такого OS-сбоя в живом исполнителе не измерялась.

Исправление: согласовать типизированный допуск и сохраняемый код причины для разрешённых подклассов. Не расширять исключения для cleanup, identity, source или случаев после неопределённой отправки.

### R5 P2 Кеш ошибочно обнуляет счётчик сетевых сбоев

Код: `vk_scheduler.py:407`, `tests/test_throughput_recovery.py:160–165`.

`scan_step()` считает любой результат каталога кроме budget/error успешным чтением и вызывает `technical_succeeded('read')`. При общем кеше результат complete/partial может быть получен без сетевого запроса. В результате кеш скрывает продолжающуюся неисправность транспорта и сбрасывает защиту третьего сбоя. Это противоречит правилу из `docs/THROUGHPUT_RECOVERY_V6_29_7.md:16`: кеш не доказывает восстановление чтения.

Воспроизведение: ошибка чтения → кеш без сетевого вызова → ещё две ошибки. Получено три `technical_error_deferred`, `paused=NULL`, read-streak 2 вместо остановки на третьем неуспехе. Сетевых вызовов в обработке кеша 0. Существующий тест подменяет `scan_step()` целиком и не проверяет эту реализацию.

Исправление: передавать число реальных успешно завершённых HTTP-чтений из каталога и сбрасывать read-streak только по этому доказательству. Пустая стена после настоящего HTTP может быть успехом; один кеш — нет.

### R6 P2 Долгая исправная пачка выглядит как сбой

Код: `web/app.js:148–154`, `vk_scheduler.py:333,385`.

Timeline требует heartbeat не старше 180 секунд. Во время последовательного исполнения действий heartbeat не обновляется; следующий статус может записаться только после всей пачки. Поэтому нормальные навигации, проверки и обязательные паузы могут сделать пачку оранжевой при работающем worker.

Node-воспроизведение: один и тот же running batch на 120-й секунде отображается running, на 232-й — uncertain. Это дефект индикации, сам worker от него не останавливается. Он объясняет часть визуальных сообщений «бот остановился», но не доказывает причину конкретного живого инцидента.

Исправление: безопасно обновлять сигнал жизни во время исполнения и показывать возраст сигнала отдельно от результата пачки. Не выдавать отсутствие heartbeat за доказанную остановку или неопределённую отправку, не скрывать реальные зависания.

### R7 P2 Нельзя импортировать допустимый отрицательный итог П3

Код: `vk_analytics_store.py:199–202`, формула `vk_analytics.py:109–110`.

Валидация запрещает отрицательные значения всех числовых полей, включая `p3`. Собственная методика допускает отрицательный итог из-за штрафа П3.1. Поэтому корректный официальный итог нельзя загрузить для сверки через manual/CSV/XLSX.

Воспроизведение: при П3.1 = −22, П3.2 = 0 и П3.3 = 0 калькулятор возвращает П3 = −22. Попытка `import_official()` с этим итогом завершается `ValueError: Invalid official numeric measurement`.

Исправление: раздельная валидация неотрицательных счётчиков, долей, процентов и итоговой оценки со штрафом. Ограничения остальных полей не ослаблять.

## Проверка причин остановки

Полная защитная пауза запрещает дальнейшие действия; процесс daemon при этом обычно остаётся живым в attention. Завершение процесса — отдельный результат. R3 способен вызвать оба, R4 — постоянную паузу, R6 — только ложную индикацию.

| Ситуация | Проверенное поведение и оценка |
| --- | --- |
| HTTP 429, VK 6/9/29 | Защитная блокировка и остановка; сохранять |
| CAPTCHA в браузере, несовпадение identity/source/date/destination, небезопасный cleanup | Немедленный fail closed; сохранять |
| API CAPTCHA 14 / проверка 17 | Общая блокировка отсутствует; дефект R1 |
| Неавторизованный uncertain или прерванное durable intent | Остановка без повторной отправки; сохранять |
| Разрешённый технический сбой до intent | Один повтор / ограниченный backoff по действующей policy; R4 нарушает классификацию |
| Три неуспешных логических действия подряд | attention по согласованной policy; успех сбрасывает отдельный счётчик |
| Три технических сбоя чтения подряд | attention по согласованной policy; R5 может скрыть достижение порога |
| Занятый профиль или activity lease | Ожидание/пропуск без принудительной остановки владельца |
| Закрыто окно, исчерпана квота, аккаунт отключён до intent | Завершение пачки без общей защитной паузы |
| Бюджет чтения, cutoff, неполный свежий pool | Без действий по старым данным; следующая штатная пачка, без catch-up |
| Добавление нового отключённого аккаунта | Должно быть безопасным управлением; дефект R3 |

## Проверки и границы

Проверены поддерживаемые пути scheduler/state/retry, исполнителя и защит, общего API-каталога и кеша, статистики, analytics collect/store/report/import/scheduled/web, управления аккаунтами и панели; установщики Windows-задач просмотрены статически. Исторические ручные команды не исполнялись. Живая доступность VK и полнота фактических данных VM не проверялись.

Полный `python -X utf8 -m unittest discover -s tests -v`: **654 теста, 137.960 секунды, OK**, без skips в локальном прогоне. Python 3.14.3, Playwright 1.64.0. Компиляция исходников также прошла. Тесты запускались в отдельной копии исходников/tests/web с публичным `vk_groups.json`, без реестра, bindings, SQLite, профилей, runtime markers и секретов. VK не вызывался; браузерные тесты использовали локальные HTML fixtures.

Все семь дефектов дополнительно воспроизведены и перепроверены основным ревьюером на временных данных. Успех существующих тестов не покрывает найденные граничные сценарии. Не включено в подтверждённые замечания: SQLITE_BUSY от стороннего писателя до действий тоже приводит к attention, но обычный поддерживаемый сценарий такой конкуренции не установлен.

Артефакты: `outputs/code-review-2026-10-26/` — полный unittest.log, reproductions.log, самостоятельные синтетические скрипты, официальная схема ошибок VK 5.199 и SHA256 исходников. `run-reproductions.ps1` создаёт новую копию только кода в `%TEMP%`; опция `-FullTests` повторяет существующий тестовый набор. Без опции запускаются только воспроизведения. Скрипты демонстрируют наличие дефектов и не являются исправлениями или приёмкой production.

Приоритет исправления: R1 и R2, затем R3/R4 для устранения лишних полных остановок, R5/R6 и R7. Исправления требуют отдельных регрессионных проверок; текущая защитная пауза и исторические uncertain этим ревью не снимаются.
