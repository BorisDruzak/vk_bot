## Что показывает отчёт

В обзоре панели раскрывается «Диагностика времени и полноты пачек».
Для каждого сохранённого слота показаны его начало, следующий слот, конец дня,
фактический захват, конец обновления счётчиков, готовность интервала и первый
durable intent. Первый intent соответствует `last_action_batch.at`, а не
открытию браузера или подтверждению VK.

При B = min(следующий слот, конец дня): срок чтения Dread = B−120с;
срок нового intent Dintent = B−60с; предел клика = min(B−20с, E−5с).
Фактический timeout финального клика по-прежнему максимум9с. Отдельно показаны
измеренное окно от готовности интервала до Dintent, попытки и verified.
Текущий `intent_closed` считается на момент запроса отчёта; сохранённые отметки
остаются историческими. Для последнего слота B = конец сохранённого дня.

Причины различают поздний захват, ожидание540с, срок чтения, срок intent,
отсутствие кандидата, квоту, защиту VK, другую защитную остановку, stop и смену
дня. `attention` без доказанного platform reason не называется защитой VK.
Незахваченный слот после S+120с отмечен пропущенным без догоняющего запуска;
это наблюдение о доступности claim, а не доказательство причины отсутствия worker.

Если после трёх попыток срок нового intent закрылся, отчёт явно указывает:
четвёртая операция не запускалась, intent и попытки нет. Диагностика не принимает
решения запускать или пропускать действия и не создаёт дополнительных jobs.

320 — теоретическая вместимость80×4, а не гарантия320подтверждений.
Сохранённые наблюдения считают новые actor reservations идемпотентно по
job/attempt_id, включая разрешённые повторы. Подтверждения отделены от попыток.
Исторические слоты без новой телеметрии показывают счётчики по jobs; переносимый
повтор может ограничивать точность привязки старой попытки к конкретному слоту.
История не пересчитывается и не мигрируется ради заполнения отчёта.

## Измерения этапов

`vk_action_timing.StageTimings` измеряет monotonic spans:

| Этап | Измеряемая операция |
| --- | --- |
| browser_open | Запуск persistent browser context |
| source_navigation | Переход к точному источнику |
| source_guard | Проверки защиты и точного аккаунта |
| community_prepare | Подготовка диалога назначения |
| click | Только реальный финальный outward click, без подготовки диалога |
| confirmation | Проверка результата, в том числе recovery без повторной отправки |
| cooldown | Реальная обязательная пауза после попытки |

Spans буферизуются в памяти. `stage_timing` записывается в существующий
`scheduler_diagnostics` после cleanup и завершения action-run, без нового
commit между проверкой финального deadline и кликом. Ошибка наблюдателя или
часов не меняет результат действия, исходное исключение и обязательный cooldown.
Неизвестное время остаётся null/«—». Прерванные spans считаются отдельно;
median и nearest-rank p95 вычисляются только из полных измерений.
Вложенные guard/confirmation spans могут пересекаться, складывать их нельзя.
Распределения используются для анализа, не для гарантии пропускной способности.

`batch_timing` пишется после штатного завершения записи результата пачки;
claim/refresh/spacing timestamps собираются только как наблюдения.
Новые таблицы и переписывание прежних событий не требуются. Read-only snapshot
не вызывает State-init, миграции или VK. Повреждённые записи пропускаются;
при общей ошибке timing остальные данные панели доступны с явной отметкой.
Выборка ограничена20000timing-событий нужного дня и сообщает об усечении.
Никаких cookies, DOM, текстов исключений, токенов и ID аккаунтов в spans нет.

## Детерминированная офлайн-симуляция

```powershell
python vk_schedule_simulation.py --incident > incident.json
python vk_schedule_simulation.py > saved80-simulation.json
python vk_schedule_simulation.py --input scenario.json > result.json
```

CLI создаёт только временные actor/scheduler SQLite и удаляет их после работы.
Профили, реестры аккаунтов и живые базы не используются. В нём работают настоящие
Worker/State/RetryLedger guards с FakeClock, а refresh, выбор кандидата и отправки
заменены синтетическими адаптерами. Временные базы не делают physical fsync;
симуляция не проверяет crash durability.

Default fixture содержит все80сохранённых начал из технической спецификации,
с интервалами545–623с. Подготовка47–48с и cooldown20с взяты из разобранного
эпизода; confirmation/cleanup — явно моделируемый остаток. Round-robin или
seeded sampling воспроизводимы. Модель не предсказывает живой состав кандидатов,
сеть, состояние аккаунтов, CAPTCHA или достижение дневной квоты.

Исходный эпизод: предыдущее начало09:25:38.071, слот09:29:21, refresh до
09:29:57, spacing до09:34:38.071, Dintent09:37:56. Текущий исход3/4 воспроизведён
как ожидаемое поведение:3попытки/3verified, окончание09:38:14.315.
Один default80-сценарий даёт310попыток/310синтетических verified,
70полных/10неполных/0пустых/0пропущенных пачек. Это результат модели.
Длинные confirmation и поздние claim воспроизводят пропуски следующих слотов
после S+120 без catch-up; next_slot_offset_seconds показывает смещение конца
пачки относительно следующего начала (отрицательное — время ещё осталось).

JSON входа:

- `day`, `slots`: сохранённые начала HH:MM:SS либо aware ISO; новые не генерируются.
- `first_slot`/`last_slot`, `claim_offsets`, `previous_action_at`/`previous_action_slot`.
- `stages`: массивы `preparation`, `cooldown`, `confirmation_cleanup`, необязательно
  `click`; `sampling`: round_robin/seeded, `seed`.
- `refresh_seconds` либо `refresh_reads`/`refresh_pages` с `{seconds,outcome}`;
  outcome: ok/network/429/captcha; `api_budget`≤5000.
- `outcomes`: verified/already/fail_before_intent/fail_after_intent;
  `stop_at`, `empty_pool`, необязательно валидируемая существующим policy конфигурация.

HTTP20, API pacing5, сетевые паузы5/10 проверяются как явно заданные входные
длительности/исходы модели. Это не проверка реального transport или его
классификации retry eligibility; существующие transport-regressions сохранены.
