## Подтверждение аккаунта

Сохранённая привязка VK ID описывает ожидаемый аккаунт, но не доказывает вход.
`vk_authentication` хранит отдельное наблюдение точной ссылки собственного
профиля из шапки VK: аккаунт, профиль, машина, ожидаемый/наблюдаемый ID и время.
Срок свежести — 300 секунд. Cookies, токены и DOM в доказательство не записываются.

`matched` требует совпадения с привязкой; другой или уже занятый другим
профилем ID даёт `wrong_account`. Отсутствие точной ссылки —
`not_authenticated` (вход не подтверждён), а не доказательство выхода из VK.
Нет свежего наблюдения — `unverified`/`stale`. Legacy `ready` и поле
`detected` не позволяют завершать вход или включать аккаунт в очередь.

«Проверить вход» запускает читающий браузер именно с выбранным профилем.
Проверяющий процесс закрывает только созданный им контекст. Новый запрос
проверки отменяет прежний положительный proof до запуска; неудача не оставляет
старое разрешение включения. CLI также сохраняет отрицательное наблюдение
до отказа в привязке. Пользовательский `--bindings` не пишет proof основной
установки. При завершении интерактивного входа ID сверяется ещё раз.

Фактическая проверка на VM: профиль №1 — вход не подтверждён; в профиле №2
открыт ID, закреплённый за №1, поэтому `wrong_account`. Оба аккаунта отключены.
Привязки, профили и история не переставлялись. Вход пользователя в правильные
профили ещё необходим; проверка не даёт разрешения автоматически включать очередь.
Состояние со временем становится `stale`, и UI показывает время наблюдения.
После запроса кнопкой UI опрашивает только локальный `login_status` каждые3сек,
не открывает браузер повторно и не сбрасывает незаписанный диалог. Во время
`opening` прежнее подтверждение сразу сбрасывается. `ready` версии2 разрешает
finish, а enable требует завершённого входа и свежего matched.

Один живой проверяющий процесс завершился с `PermissionError`; точное место
исходного сбоя не сохранено, причина UNKNOWN. Отдельно на Windows воспроизведён
WinError5 при атомарной замене JSON, который ещё читает другой поток. Добавлены
не более6 попыток только замены локального файла, ожидание суммарно<=0.75сек,
только Windows errors5/32/33. При стойком отказе ошибка сохраняется и вход не
подтверждается; VK операции не повторяются. Диагностика новых ошибок содержит
только тип, errno и имена/строки модулей проекта, без текста исключения/DOM.
После установки повторная живая проверка№2 завершена `checked/wrong_account`,
результат появился автоматически без ручного обновления страницы.

## Статистика

Для каждой из 57 настроенных групп показываются до 100 последних сохранённых
публикаций VK API, диапазон дат публикации и диапазон времени наблюдения.
Поля: лайки, комментарии, репосты, просмотры. Полная сумма возвращается только
при известном счётчике каждой записи; иначе — известная сумма и покрытие K/N.
NULL не превращается в ноль, включая просмотры. Кнопка «Публикации» открывает
записи конкретной группы с исходными счётчиками. Это выборка, не вся стена.

«Обновить через API» делает один `wall.get(count=100, offset=0)` на выбранную
или каждую настроенную группу. Используются существующий key, общий журнал
чтений, бюджет 5000/скользящие 24 часа и пауза не меньше 5 секунд. Курсоры полного
каталога не двигаются. Ни браузерных действий, ни попыток/резерваций обновление
не создаёт. VK 429/защиты сохраняют остановку; 7 отмечает недоступную группу.

Один фактический ответ содержал 100 записей, из которых 98 проходили прежний
`_valid_post`. Ранее отклонялась вся страница. Теперь валидные записи сохраняются,
непригодные исключаются, результат `partial`. Проверка источника не ослаблена;
дубли ID, неверный envelope и полностью непригодная непустая страница запрещены.

Живой проход из веб-панели завершён: 57/57 групп, 57 запросов, один частичный
ответ, две исключённые записи. Данные просмотров есть у всех 57 групп:
5677/5700 публикаций текущей выборки. Лайки/репосты известны5700/5700,
комментарии5699/5700. Остальные просмотры/комментарии явно неизвестны;
разница не равна только двум исключённым записям: выборка включает сохранённые
публикации, и head API может не обновить каждую из них. Время наблюдений видно
в панели. Формулы вовлечённости пока не определены и не вычисляются.

## Согласование и проверка

OS lease `.vk-activity.guard` согласует целую пачку worker с входом и читающим
обновлением статистики; затем действуют прежние global/profile locks. Занятый
lease откладывает чтение/пачку до claim, не увеличивает техническую серию ошибок
и не снимает чужие блокировки. После аварии OS освобождает lease самостоятельно.
Статус фонового обновления старше 1900 секунд считается потерянным только при
свободном OS guard; UI разрешает новый ограниченный проход без reset API ledger.
