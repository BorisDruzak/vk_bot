# Диагностика публичного чтения и доступа —26октября2026

Прямой запрос: добавить логирование причин тайм-аута/сетевой доступности;
отдельно объяснить лучший способ избежать нехватки времени подготовки.
Изменение реализует только диагностику чтения. Правила времени действий,
heartbeat/UI, повторы, лимиты и защитные паузы не меняются.

## Что фиксируется

Новый vk_read_trace.py наблюдает за исходными stdlib-вызовами только в
существующем одноразовом HTTP-only helper. Наблюдатели делегируют исходные
аргументы/результаты/исключения и восстанавливаются в finally. Настройки
сертификатов, TLS, прокси и фактические запросы не меняются.

Фазы: запуск helper, импорт модулей, чтение stdin, открытие HTTP, DNS,
TCP connect, TLS handshake, отправка запроса, заголовки, тело и JSON parse.
Последний достигнутый этап сохраняется через ограниченный stderr-протокол
даже при уничтожении helper по прежнему общему20сек timeout.

В scheduler_diagnostics и vk_scheduler.log появляются public_read_finished
и public_read_failed с полями:

- read_id — случайный идентификатор одного физического чтения;
- source_group/slot — публичный источник и текущая пачка;
- read_phase/read_error — фиксированные коды этапа и причины;
- elapsed_ms/timeout_ms/phase_elapsed_ms/helper_start_ms/read_timings_ms;
- числовые errno/winerror/tls_verify_code/http_status/vk_error_code;
- bytes_received при завершённом чтении тела и read_exit_code при сбое helper.

Примеры причин: dns_error,access_denied,connection_refused,connection_reset,
network_unreachable,tls_certificate_error,tls_error,timeout,helper_deadline,
http_rate_limited,vk_rate_limited,vk_access_denied,invalid_json,response_too_large.
HTTP429 и ограничение VK кодом6 остаются разными диагностическими источниками;
прежняя защитная блокировка при ограничении сохраняется.

Безопасный пример искусственного сбоя:

```json
{"event":"public_read_failed","read_phase":"tls_handshake","read_error":"helper_deadline","elapsed_ms":20015,"timeout_ms":20000}
```

Сырые stderr, argv, URL, хосты/IP DNS, заголовки/тела, токены, cookies,
тексты исключений и их поля reason/message не передаются в журнал.
Протокол принимает только ограниченные enum/числовые поля; произвольные
строки/ключи отбрасываются. Успешный ответ VK сохраняет прежние JSON-поля;
metadata находится в атрибуте внутреннего двухэлементного tuple результата.

Ошибки API5/7/28 после успешного HTTP также сохраняют read_id/время в
исключении VKReadClient и общем scheduler_failed.error_chain.public_read.
Коды и прежняя retry/auth/rate-limit policy не меняются.

Запись диагностического события выполняется только ПОСЛЕ чтения, чтобы
задержка записи SQLite не могла отложить HTTP после финальной проверки
deadline и резервирования API ledger. Ошибка callback не меняет результат.
Полнота pool и deadline/stop/window после чтения проверяются прежним кодом.

Охват: подробные фазы получает bounded_transport в предбатчевом refresh.
Обычный прямой catalog transport не переведён на другой клиент этой правкой.
При отсутствии этапных записей остаётся helper_start/unknown, а не выдуманная
причина DNS/TLS. Последний этап локализует ожидание, но сам по себе не доказывает
вину конкретного сервера: возможна, например, задержка исполнения процесса.
Исторический тайм-аут09:30 новым логированием задним числом не восстанавливается.

## Рекомендация по нехватке времени — не реализована

Job526 начали готовить09:09:52 при intentcutoff09:10:23: оставалось31сек,
подготовка закончилась09:10:38, примерно через47сек. Финальная защита правильно
отменила отправку без intent/attempt, но поздно начатый job получил failed.

Предпочтительное изменение — admission check до create_job/начала подготовки:
оценивать оставшееся время до intentcutoff по недавнему P95 подготовки данного
типа действия с резервом; при малой истории использовать консервативный fallback.
Отдельно учитывать оставшееся время до click boundary/конца окна и cooldown20.
Если запаса нет — завершать текущую пачку штатным partial/deferred без создания
failed job/intent и без расхода попытки. Неотправленный кандидат остаётся для
обычного выбора в следующей штатной пачке при свежих данных и прежних guards;
закрытые пачки не переоткрываются и дополнительные догоняющие слоты не создаются.

Финальные проверки перед intent/click сохраняются: оценка не гарантирует
длительность сети/UI. При64группах полный обход по5сек уже может занять больше
5минут; четыре действия не гарантированы в каждой9минутной пачке. Для гарантии
полных квот потребовалось бы отдельно пересмотреть фактическую пропускную
способность, а не сокращать защиты/паузы или использовать старые счётчики.
