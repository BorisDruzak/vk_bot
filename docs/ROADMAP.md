# План продолжения VK Unified после v6.24

## Приоритет P0 — Git и воспроизводимость

- [ ] Проверить GitHub `main` и корректную установку на чистом Windows-ПК без секретов.
- [ ] Вынести настройки реальных аккаунтов из репозитория. Не коммитить текущие SQLite/Chromium/Cookies/VK API ключ.
- [ ] Добавить детерминированный CI: компиляция Python, unit-тесты базы/аккаунтов/API с fake transport; браузерные тесты в отдельный timeout/fixture без сети.
- [ ] Проверить, что тесты не меняют рабочую SQLite и не требуют действующего VK.

## Приоритет P1 — эксплуатационная архитектура

- [ ] Разделить модель `Post` (общая, из VK API) и `AccountPostState` (строго по VK ID).
- [ ] Написать миграцию существующей истории аккаунта №1 без потери `verified`, `already`, `uncertain` и журналов.
- [ ] Выполнить повторный `--check-account` для обоих профилей перед любым чтением их состояний; неожиданный VK ID → fail closed.
- [ ] Отдельно тестировать изоляцию авторизованных сессий, кеша состояния, предупреждений и CSV.
- [ ] Не вводить согласованное массовое увеличение вовлечённости с нескольких профилей; многопрофильность сейчас для независимого управления и диагностики.

## Приоритет P1 — полнота VK API

- [ ] Восстановление после частичных `wall.get` выборок, корректная граница семи суток.
- [ ] Диагностика недоступных/закреплённых записей, сохранять источник timestamp.
- [ ] Отчёт 57 групп: complete/partial/error, последняя успешная дата/время, число свежих записей, причины откладывания.
- [ ] Повторное сканирование только когда истёк cache TTL; реакция на HTTP 429 и VK error codes — стоп.

## Приоритет P2 — мониторинг и UX

- [ ] `--doctor` локально: проверка зависимостей, доступность Chromium, схемы SQLite, состояния lock-файлов, отсутствие секретов в repo.
- [ ] CSV/XLSX отчёты по группам и задачам, понятные причины пропусков и неполных результатов.
- [ ] Простой read-only dashboard позже, только при практической необходимости.
- [ ] Точное описание CLI + стабильная машина состояний для `pending/already/verified/uncertain`.

## Правила приемки

После каждого изменения: тест на временной SQLite, unit/regression, отсутствие живых запросов из CI, проверка `.gitignore`, `git diff --check`, отчёт об известных ограничениях. Применение изменений к рабочему аккаунту — только с явным запуском оператором. При VK rate limit не предпринимать автоматические повторные попытки до ручной проверки.
