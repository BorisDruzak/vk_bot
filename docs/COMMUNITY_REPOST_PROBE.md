# Диагностика выбора сообщества для репоста

Дата: 2026-10-21. Этап: проверка видимости и пути выбора на реальном VK, без отправки репостов. Исполняемый код остаётся v6.26; поддержка публикации в сообщество в CLI пока не добавлена.

Ссылки для определения этих четырёх назначений не потребовались: ID и названия прочитаны из списка сообществ в соответствующем авторизованном профиле. Числовые ID самих пользователей, cookies и токены в отчёт не включены.

В каждом случае проверены: точная опция по `data-testid`/`value`, ожидаемая подпись, затем фактическое значение поля `input[role="combobox"]` после выбора. Радиокнопка `club` включена, `message` выключена, финальная кнопка отправки видима и активна. Активность кнопки не подтверждает успешную публикацию: финального клика не было.

## Проверенный путь и селекторы

1. Запустить отдельный сохранённый Chromium-профиль; сверить авторизованный VK ID с его локальной привязкой. Профили проверялись последовательно под штатными lock-файлами.
2. Открыть один точный API-пост. Проверить корневой контейнер, основной `article` и единственную кнопку репоста тем же `POST_FOOTER_ACTION_JS`, который используется в v6.26. Открыть только диалог «Поделиться».
3. Найти единственный видимый `label[data-testid="club_share_option"]`. В обоих профилях получено `radio "В сообществе"`; выбор подтверждён через `input[name="shareOption"][value="club"].checked`.
4. Найти `[data-testid="share_club_select"]` и вложенный `input[role="combobox"]`. Дождаться завершения состояния «Список опций загружается...». Наличие самого поля ещё не означает, что список готов.
5. Раскрыть список. На аккаунте 1 устойчиво проверен клик по `svg.vkuiIcon--dropdown_20` внутри `share_club_select`. На аккаунте 2 сработало раскрытие контейнера и клавиша `ArrowDown`. Только клик по текстовому input или взаимодействие до загрузки списка не были устойчивыми. При проверке через MCP отдельную страницу профиля нужно выводить на передний план.
6. Выбрать ровно одну опцию `[data-testid="share_club_option_<ID>"]`, предварительно сопоставив её `value` и `label` с ожидаемым назначением.
7. Дождаться точного ожидаемого `input.value` в поле сообщества. Повторно проверить `club.checked=true`, `message.checked=false`. Не использовать один лишь `aria-selected`: после повторного раскрытия/клавиатурной навигации он не дал устойчивого подтверждения фактического значения поля.
8. `[data-testid="share_tab_submit"]` только проверялась на видимость/активность. На этом диагностический проход остановлен; вкладки и диагностические контексты закрыты.

Важное наблюдение: при открытии диалога в обоих аккаунтах было выбрано **личное сообщение** (`message=true`), а не личная стена или сообщество. Назначение нельзя предполагать по умолчанию или по последнему запуску.

## Отсутствие действий и состояние после проверки

Во временных диагностических страницах установлен дополнительный перехват финальной кнопки и отправки формы. Число попыток нажать финальную отправку — 0. Рабочие `run-actions`, `process_one` и публикационные методы не вызывались.

- Аккаунт 1: число `action_attempts` до и после — **71**.
- Аккаунт 2: число `action_attempts` до и после — **62**.
- HTTP 429 и предупреждений защитной проверки в диагностических проходах не обнаружено; сохранённых предупреждений в обеих SQLite после проверки — 0.
- Диагностические контексты закрыты, lock-файлы освобождены. Репосты и лайки не отправлялись.

## Граница следующей реализации

Этот проход подтверждает доступность UI выбора четырёх назначений. Он не проверяет фактическую отправку, появление записи на стене сообщества, проверку автора публикации или повторный запуск после неопределённого результата.

Для реализации нужно отдельно согласовать, в какие из доступных сообществ направлять каждую публикацию и как считать бюджет при нескольких назначениях. История репостов должна учитывать аккаунт, исходный пост и целевое сообщество; существующий общий `posts.repost_status` описывает прежний сценарий и не доказывает репост в каждое назначение. Подтверждать будущую отправку следует по конкретной целевой стене и ссылке на исходный пост, а не только по флагу репоста у источника. Текущие личные репосты и их история должны сохраняться.

Рабочие файлы v6.26, реальный тест 30/30 и его результаты этим диагностическим этапом не изменены. Привязки назначений пока зафиксированы только в этом локальном отчёте, а не добавлены в конфигурацию выполнения или GitHub.
