# v6.29.5 — подтверждённый пропуск без расхода квоты

По прямому запросу пользователя добавлен автоматический пропуск выбранного действия обоих аккаунтов в ежедневном scheduler, только ДО резервации и финального клика. Он разрешён при прямом положительном доказательстве запрета со стороны VK, а не по отсутствию кнопки/ошибке селектора.

## Что считается доказательством

Используется JSON wall.getById, уже загруженный авторизованной страницей VK: текущий cache и сохранённый inline JSON. Новых запросов к запрещённому нашим ключом wall.getById нет. Проверяются точные owner/id/date, HTTPS/разрешённый хост/маршрут, единственный основной root, правильный профиль и отсутствие защит VK. Два согласованных чтения через350мс и финальная проверка профиля/защит должны подтвердить:

- like: user_likes=false и likes.can_like=false;
- personal/community: user_reposted=false и likes.can_publish=false либо likes.repost_disabled=true.

Семантика полей сверена по официальной [схеме VK API5.199](https://raw.githubusercontent.com/VKCOM/vk-api-schema/master/base/objects.json), base_likes_info. Context7 недоступен по месячной квоте. Строковые/неизвестные значения не превращаются в boolean. Чужой/вложенный пост, несовпадение даты, противоречие cache/inline, изменение флага между чтениями не разрешают пропуск. Уже существующая реакция проходит прежнюю проверку результата; она не называется новым VK-пропуском.

Это доказательство текущей недоступности выбранного действия для этого профиля/поста, а не доказательство внутренней ошибки серверов VK. CAPTCHA429/проверка входа/несовпадение профиля всегда останавливают. Скрытая панель без явного запрета остаётся UNKNOWN: ошибка разметки/скрипта не маскируется VK-пропуском. Для старого job61 это автоматически не доказывает серверный запрет; его отдельное unresolved-решение сохранено.

## Лимиты и журнал

execute_action возвращает skipped_vk/attempt_id=NULL до process_one/chooser. State дополнительно проверяет dispatching/no attempt, actor pending, отсутствие uncertain/error/предупреждений и новой попытки выбранного действия. Уже зарезервированное действие пропускать нельзя: прежний uncertain/расход лимита сохраняются. Community-проверки canonical refs/истории/назначения предшествуют проверке запрета.

Job сохраняется failed с фиксированным reason vk_like_denied/vk_repost_denied, без attempt. scheduler_skip_evidence и last_vk_skip хранят только основание, поле, boolean-значение, два чтения и время. Actor статусы остаются pending, истории попыток и квоты не уменьшаются. --scheduler-status показывает vk_skips и last_vk_skip. Уникальность дневного job исключает повторный выбор того же действия/назначения/поста в этот день; на следующий день разрешена новая читающая оценка.

Планировщик выбирает следующий пост внутри той же пачки: максимум4реальных попытки и прежний предел8выборов, чтобы цепочка пропусков не стала бесконечной. Окно09–19YEKT,50/10/20 на аккаунт,community10+10,sleep20 после каждой попытки,>=10мин между фактическими пачками, прежний случайный план и запрет catch-up сохраняются. Отдельные ручные CLI-режимы не изменены.
