## Расчёт

Приложение1, пункты3–3.3 предоставленной методики, страницы11–13:

```
ER = (sum(likes)+sum(comments)+sum(reposts))/sum(views)*100
П3.3 = min(100, ER/3.6*100)
П3.2 = min(100, G/(C-Cv)*100)
П3 = штраф П3.1 + 0.5*П3.2 + 0.5*П3.3
```

Контроль180+50+40/10000: ER2.7%, П3.3=75%. Используется Decimal для границы3.6.
V берётся только из `views.count` основной публикации, не охват и не
`copy_history`. Сначала суммируются исходные числа. NULL сохраняется: при
неполном архиве/счётчиках окончательный ER не выдаётся, известные суммы и
отношение только полных строк доступны отдельной диагностикой. V=0 даёт
неопределённый ER, а не нулевой. Будущий незавершённый период — partial.

Основной округовой ER — отношение общих сумм. Средний ER страниц — отдельный
diagnostic_mean с K/N; страницы с неопределённым ER не становятся нулями.
П3.1 не выводится из статистики стены. `--p31-ratio` принимает отдельно
подтверждённую долю соответствия0..1 и применяет штрафные градации методики;
без этого П3 остаётся UNKNOWN. Автоматической проверки виджетов/оформления нет.

## Периоды и регулярность

Все даты CLI — YEKT, `[start,end)`: для8–14октября `--start 2026-10-08
--end 2026-10-15`. Публикации отбираются по дате размещения, счётчики накоплены
к моменту текущего API-чтения. Это не приращение реакций/просмотров в периоде.
Прежние значения нельзя восстановить без прежних снимков.

`--weeks period` — отрезки7дней от начала; `calendar_clip` — понедельник–воскресенье
с обрезкой краёв периода; `calendar_complete` — только полные календарные недели;
`calendar_full` — полные пересекающиеся недели, UNKNOWN при отсутствии данных
вне периода. Порог всегда3 в учитываемую неделю; любая проваленная неделя
означает невыполнение страницы. Показываются все недели и список проваленных.
`--exclude-reposts` исключает top-level copy/repost из расчёта и регулярности.
Неизвестные правила недель, репостов и список страниц-визиток требуют ЦУР.

## Хранение

`vk_analytics.sqlite3` — самостоятельная база. Открытие actor/scheduler базы
как аналитической отклоняется по чужим таблицам до миграций.

- `analytics_publications`: ID сообщества/поста, дата, URL, тип, закрепление,
  признак репоста, source и первоначальная доступность.
- `analytics_snapshots`: run/group/post, UTC микросекунды, nullable L/K/R/V,
  source/status и метаданные на момент измерения. Текущую доступность нужно
  читать из снимка нужного запуска; первоначальные метаданные не перезаписываются.
- `analytics_runs`, `analytics_run_groups`: период, начало/конец, покрытие,
  ошибки, checkpoints, сохранённый состав, included/business_card, baseline count.
- `analytics_reports`: месяц, вариант, fixation UTC, суммы, ER/П3.3/П3.2,
  completeness, версия правил, полный frozen JSON со всеми группами и сверкой.
- `analytics_official`: неизменяемые импортированные официальные замеры;
  `analytics_capabilities`, `analytics_errors`, `analytics_page_diagnostics`:
  безопасные ошибки/возможности/числовые метаданные неполных страниц.

Новый запуск создаёт новые снимки; `(run,group,post)` исключает дубли при resume.
Каждая страница и checkpoint фиксируются атомарно. Незавершённая группа
возобновляется с головы: сохранённые offset не используются вслепую после
изменений стены. Изменение count или исчезновение уже наблюдавшегося ID
сохраняет partial; нужен новый запуск для нового состояния. Ранее известный
пост, не найденный в новом полном проходе, сохраняется с NULL/not_returned,
что не является доказательством удаления. By-ID tombstones дают deleted/NULL.

## Запуск на основной VM

Только новые модули аналитики установлены рядом с существующим проектом.
Runtime binding `.vk-analytics-runtime.json` содержит hostname/root VM и
проверяется до чтения ключа. Локальная копия со своим старым ledger не может
случайно начать параллельный сбор. Ключ читается прежним `configured_token`.
Каждый запрос держит существующие activity/global guards, общий ledger5000/24ч
и API pause>=5сек. Профиль не открывается. HTTP429/VK rate codes сохраняют
действующую safety lock. Авторизацию и ошибки чтения автоматически не повторяем.
Занятость worker — deferred; `--wait-busy-seconds 600` ждёт только занятость,
до600сек, без stop/unpause/удаления locks. Общий `--max-requests` ограничен5000.

```powershell
$py = '.venv/Scripts/python.exe'
& $py vk_analytics_cli.py import-official 'путь-к-файлу.xlsx' --start 2026-10-08 --end 2026-10-15 --as-of 2026-10-16 --registry-out analytics_local/sosnovsky.json
& $py vk_analytics_cli.py collect --registry analytics_local/sosnovsky.json --start 2026-10-08 --end 2026-10-15 --live --max-requests 250 --wait-busy-seconds 600
& $py vk_analytics_cli.py collect --resume RUN_ID --live --page-size 20
& $py vk_analytics_cli.py report --run RUN_ID --weeks period --official-import IMPORT_ID --out analytics_local/report --freeze
& $py vk_analytics_cli.py status
```

Реестр JSON — массив `{id,name,included,business_card}`; положительные уникальные
community ID. Изменяйте его до нового запуска: существующий run и frozen report
сохраняют прежний состав. Старый `vk_groups.json` не меняется. Неподтверждённые
визитки пока имеют business_card=false, поэтому П3.2 предварителен.

`wall.get`: count1..100, страницы до доказанной границы дат/конца стены,
старый pinned не завершает сканирование. Mixed/невалидная/нестабильная страница
остаётся partial. Читать меньшими страницами допустимо, если новый проход
полностью доказывает границу выбранного периода и согласованность ID.

```powershell
& $py vk_analytics_cli.py probe-by-id --run RUN_ID --batch-size 2
& $py vk_analytics_cli.py collect --registry analytics_local/sosnovsky.json --start 2026-10-08 --end 2026-10-15 --live --refresh-from OLD_RUN --batch-size 100
```

By-ID batch1..100 проверяет точные ответы; неподдерживаемый1051 записывается
как capability и используется обычный wall.get без обхода ограничений. Обновление
только известных ID не доказывает полноту архива: статус known_posts_only/partial.
Документация API: https://github.com/VKCOM/vk-api-schema/blob/master/wall/methods.json
На реальном пакете2 текущий ключ вернул1051; успешный большой пакет не заявляется.

## Импорт и сверка

Поддержаны CSV (UTF8, `;`/`,`/tab), XLSX (cached values, без выполнения формул),
частичные данные и `manual --json`. Канонические поля:
`period_start,period_end,measured_at,as_of_date,group_id,name,posts,likes,comments,
reposts,views,er,p33,p32,p3,p31_ratio`. Проценты — процентные пункты, ER2.7,
а не0.027. UTC/offset обязателен, если задано точное measured_at. Отсутствующие
поля остаются неизвестными. group_id=null/отсутствует — округ. Название
муниципалитета в CSV/XLSX фильтруется точно. Официальные листы и generic layout
поддержаны; сырой справочник с повторами не смешивается с официальным перечнем.

```powershell
& $py vk_analytics_cli.py manual --json '{"period_start":"2026-10-08","period_end":"2026-10-15","group_id":null,"p33":77.03}'
```

Импорт `--start/--end` не подтверждает реальные границы ЦУР: по умолчанию
period_status=unconfirmed. Отчёт показывает абсолютную/относительную разницу,
время, полноту, условность совпадения периода, составы и перерасчёт официальных
сумм. Одного официального П3.3 недостаточно для восстановления исходной выборки.
HTML/JSON/CSV выгружаются без API. Полные исходные данные остаются локальными.
